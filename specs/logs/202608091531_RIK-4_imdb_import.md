## Summary

Implemented the user-facing IMDb CSV import: an upload form at `/importar` with a
Calificaciones/Lista de seguimiento selector, a synchronous Server Action that parses the CSV,
matches or creates stub `media_items`, and upserts `user_media_status` under RLS, and an inline
summary of the result. Also added the missing authenticated INSERT policy for stub creation, which
RIK-1's RLS migration never granted.

## Scope delivered

- DB: one policy-only migration granting authenticated INSERT on `media_items` (scoped to
  `is_stub = true`), `genres`, `people`, `media_genres`, `media_people`.
- Types: `MediaItem`, `Genre`, `Person`, `UserMediaStatus`, `ImdbImportBatch`, `ImdbImportRow`,
  `ImdbCsvSourceType` in `types/index.ts`.
- Constants/lib: IMDb title-type → app type mapping (fail-open to `movie`); slug generation with
  DB-constraint-driven retry-on-collision.
- Ingestion: CSV parsing (papaparse, raw-string rows, per-row validity flag) and per-row processing
  implementing schema doc Section 7.3 exactly (ratings vs. watchlist paths, `manually_edited` guard).
- Services: `ImdbImportServices` centralizing all Supabase query shapes (batch lifecycle, media
  find-or-create with genre/director linking, `user_media_status` upsert with the manually_edited
  branch, row logging).
- Actions: `importImdbCsv` Server Action (`useActionState`-compatible), session-checked, revalidates
  `/panel`, `/biblioteca`, `/recomendaciones`.
- UI: `UploadForm` + `ImportSummary` client components; `card`, `input`, `alert` reused, `radio-group`,
  `progress` (installed, unused pending a progress signal — see Deferred), `table`, `badge` added via
  the base-lyra shadcn registry; `app/(app)/importar/page.tsx` route shell.
- Config: `experimental.serverActions.bodySizeLimit = "4mb"`; added `papaparse` +
  `@types/papaparse`.

## Decisions

- **Stub-insert RLS policy (clarify_before_coding #1):** confirmed via the real migration files
  that RIK-1's RLS migration granted only `SELECT` on the catalog group — no authenticated write
  policy existed at all. Added `supabase/migrations/20260809151800_imdb_import_stub_insert_policies.sql`,
  scoping `media_items` to `with check (is_stub = true)` and leaving `genres`/`people`/
  `media_genres`/`media_people` open to any authenticated insert (they have no owner/stub concept
  of their own).
- **Genre/director linking (clarify #2):** implemented as described in Phase 3/4, only when a stub
  is newly created (not on a `matched` row), per Section 7.3's own scoping of columns to the create
  step.
- **RadioGroup over Tabs (clarify #3):** used for the source-type selector, per the ticket's default.
- **`want_added_at` from CSV `Created` column (clarify #4):** read when present, else `now()`.
- **`user_media_status` upsert strategy:** used a single `.upsert(..., { onConflict: "user_id,media_id" })`
  for the "no existing row or not manually_edited" branch (only the columns relevant to the current
  import type are included, so the other import type's columns are never touched), and a targeted
  `.update()` for the "manually_edited, rating currently NULL" branch. This satisfies the ticket's
  own implementation_notes ("either [upsert or select-then-conditional-write] is acceptable... as
  long as it's centralized in one function") — chosen over a raw `ON CONFLICT ... WHERE` SQL clause
  because the Supabase JS client used everywhere else in this codebase doesn't expose conditional
  `DO UPDATE` clauses, and a second full statement would require an RPC function this ticket doesn't
  otherwise need.
- **`source` column reflects the most recent import that touched the row:** since `user_media_status.source`
  is a single column (not a history), running a ratings import followed by a watchlist import on
  the same title leaves `source='imdb_watchlist'` even though `personal_rating`/`watched` still
  carry the ratings import's values — each import type only ever writes the columns it owns, so this
  is inherent to a single-column "source" field, not a data-loss bug. Verified in AC-1/AC-2 testing.
- **`director` name matching uses `ilike` unescaped:** acceptable for this ticket's scope; a name
  containing `%`/`_` could theoretically over-match, considered a non-issue for real IMDb director
  names.
- **Batch `status='failed'` on any row-loop exception**, not only an unparseable file: the spec's
  ground_truth note calls out "the file could not be parsed at all" as the `failed` case, but leaving
  the batch stuck at `pending` after an unrelated DB error would be worse than marking it `failed`
  with partial counts, so `runImdbImport` finalizes as `failed` on any thrown error mid-loop too.

## Deferred / follow-ups

- **Browser file-upload click-through of `/importar` was not exercised in this session** — the
  available in-app Browser pane has no file-input automation, and the Chrome extension surface
  wasn't connected in this environment. UI structure/rendering was confirmed in the Browser pane
  (form fields, RadioGroup, labels all present and correctly wired), and the actual import logic
  was verified end-to-end against the real local Postgres+RLS instance via a script that calls the
  exact same `runImdbImport` function the Server Action calls. A human should still click through
  the real upload once — see Manual validation below.
- `Progress` component was added per Phase 7 but isn't wired up — this ticket's import is
  synchronous within one request/response (no chunked upload progress events to report), so there
  was nothing to bind it to. Left installed for a future ticket if IMDb exports grow large enough to
  warrant a progress signal.
- Import-history list and `/importar/[batchId]` detail view are RIK-5, per the ticket's own scoping.
- Auto-unmark reconciliation for watchlist "bajas" deliberately not implemented (Section 7.3, option b).
